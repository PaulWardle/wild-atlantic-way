# Handoff: Wild Atlantic Way — Trip App

## Overview
A private, mobile-first web app for a motorcycle trip around Ireland's Wild Atlantic Way, shared between the two riders ("brothers") and their friends & family ("guests"). It shows a live countdown, an interactive route map, a day-by-day itinerary, campsites, a "Signature 15" highlights list, a shared postbox (messages from F&F), a day-by-day journal, and a printable "Trip Book" export. It has a real shared backend (Supabase) so everyone sees the same data in near-real-time, plus offline-safe posting.

**Goal of this handoff:** move the app into a real codebase (via Claude Code) so it can be maintained and improved properly, and re-host it (Netlify → Cloudflare Pages). This README is written to be self-sufficient — a developer who wasn't in the original conversation can rebuild the app from it alone.

## ⚠️ Read this first — what these files actually are

The app was built in a visual design tool that uses a **bespoke component format** called a "Design Component" (`.dc.html`). **This is not a standard framework** (not React/Vue/Svelte as-shipped). Concretely:

- `WAW Itinerary Pack.dc.html` — the entire app: an HTML **template** using `{{ dotted.path }}` placeholders and custom tags (`<x-dc>`, `<sc-if>`, `<sc-for>`), plus a **logic class** `class Component extends DCLogic { … }` at the bottom (inside a `<script data-dc-script>` block). The logic class is essentially a React class component minus `render()`; `renderVals()` returns the values the template interpolates.
- `support.js` — the **runtime** that interprets the template + logic (resolves `{{ }}`, handles `<sc-if>`/`<sc-for>`, wires events). It is auto-generated by the design tool. **Do not treat this as app code to maintain** — it's the engine, included only so you can see how the template semantics work.
- `trip-data.js` — all the **trip content** as a plain JS object on `window.TRIP` (route coordinates, days, campsites, Signature 15, packing lists, etc.). This is clean, portable data you can reuse directly.
- `index.html` — the **compiled, self-contained single-file build** (template + logic + runtime + data + fonts all inlined, ~1.1 MB). This is what is currently deployed. It self-unpacks in the browser.

**The task is NOT to keep editing the `.dc.html` format.** It's to **recreate this app in a real, maintainable codebase** using the documented behavior, data model, and backend below. The `.dc.html` file is the source of truth for *look and behavior*; `trip-data.js` is directly reusable; the Supabase backend stays exactly as-is.

## Recommended target architecture

The logic is already shaped like a React class component and the styling is all inline — so the lowest-friction, highest-quality rebuild is:

- **React + Vite + TypeScript** (SPA). Convert the one `Component` class into a small tree of function components + hooks.
- **`@supabase/supabase-js`** for data + realtime (already used — same client, same tables).
- **Inline styles / CSS Modules / Tailwind** — your call; current design is 100% inline styles, easy to port to any of these.
- **Host on Cloudflare Pages** (static build output; see migration section).
- Keep `trip-data.js` as a typed `tripData.ts` module (it's plain data).

This is a **single-page app with no server of its own** — all shared state lives in Supabase, all device state in `localStorage`. That property should be preserved (it's what makes hosting trivial and offline work).

- **Security:** Row-Level Security is **open** (anyone with the link can read/write). This is intentional for a private F&F link. If you want to lock it down later, that's a future task (e.g. a shared passphrase gate on writes, or Supabase Auth).
- **Realtime:** the app subscribes to a channel named `waw` on postgres changes across all five tables; any change triggers a full re-pull (`pullAll()`).

### Tables & columns
All timestamps (`ts`) are **JS epoch milliseconds** (`Date.now()`), used as the primary sort key and de-dupe id.

| Table | Columns (as used by the app) | Notes |
|---|---|---|
| `posts` | `name` (text), `reason` (text), `msg` (text), `ts` (int8) | Postbox messages from F&F. `reason` ∈ Recommendation / Comment / Question / Feedback / Hello. |
| `locations` | `label` (text), `lat` (float), `lon` (float), `ts` (int8) | "We are here" pings the brothers post. Drives the live map position + green progress line. |
| `notes` | `body` (text), `author` (text), `tag` (text), `day` (int/text), `ts` (int8) | Journal entries by the brothers. `author` ∈ Paul / CJ. `tag` ∈ Road / Attractions / Update / Thought / Feeling / Action / Key Event / Milestone / Oh Fuck! Moment / Other (+ free text). |
| `marks` | `stop` (text, unique key), `mark` (text) | Keep / Maybe / Cut decisions per itinerary stop. Upserted on `stop`. No `ts`. |
| `sig` | `sid` (text, unique key), `ts` (int8) | Which of the "Signature 15" have been bagged, with the time bagged. |

### Data access patterns (replicate these)
- **Pull all:** `select('*')` from all five tables in parallel → normalize into the local store shape → sort posts/updates/notes by `ts` desc.
- **Insert:** `posts`, `locations`, `notes` are inserted with a client-generated `ts`.
- **Upsert:** `marks` (on `stop`), `sig` (on `sid`).
- **Delete one:** `.delete().eq('ts', ts)` (or `.eq('stop', …)` / `.eq('sid', …)`).
- **Delete all in a table:** two helpers exist because `marks` has no `ts` — one deletes `where ts > 0`, the other deletes `where <col> is not null`.

### SQL that created it (for reference / re-provisioning)
If you ever need to stand up a fresh project, the tables are simple; each needs RLS enabled with permissive policies and realtime turned on. Recreate five tables with the columns above (all nullable except the natural keys), `alter publication supabase_realtime add table …` for each, and an allow-all policy for anon `select/insert/update/delete`.

## Device state — `localStorage` + offline outbox

- **Key:** `waw2026:v1` — a single JSON blob.
- **Shape:** `{ role, posts[], updates[], notes[], marks{}, sig{}, outbox[] }`.
  - `role`: `"brother" | "guest" | null` (null = show the landing gate).
  - `posts/updates/notes`: local mirror of the cloud (so the app renders instantly offline and before the first pull).
  - `marks`: `{ [stop]: "keep"|"maybe"|"cut" }`.
  - `sig`: `{ [sid]: ts }`.
  - `outbox`: queued writes that haven't reached the cloud yet.
- **Offline outbox pattern (important — preserve it):** every write goes into `outbox` first (keyed so duplicates collapse) and is optimistically applied to the local mirror. A flush runs **every 20 s** and on the window `online` event: it replays queued ops to Supabase, drops the ones that succeed, then re-pulls. The UI shows an amber "N waiting to send" banner while the outbox is non-empty, and individual unsent items get a "not sent" tag. This is what stops people from thinking they posted when they hadn't (a real pain point that drove this design).

## Roles & access gate

- On first load (`role === null`) the app shows a **landing gate**: plain screen with the countdown, trip title and map, and two buttons — **"I'm a brother!"** and **"I'm a guest"**.
- **Brother** → a password prompt; the password is **`WAW`**. On success, `role = "brother"`, full app unlocked.
- **Guest** → no password; `role = "guest"`, restricted view.
- A small role chip in the home header lets you sign out (clears `role` → back to the gate).

### Brother vs Guest — the difference
| Area | Brother | Guest |
|---|---|---|
| Bottom nav | Home · Days · Today · **Journal** · Info | Home · Days · Today · **Postbox** · Info |
| Postbox | **Read & remove** messages (moderation) | **Post** messages; can't remove |
| Journal | Full: add/edit/remove notes, PDF + backup export | **Read-only** (browse + no note form, no backup) |
| "We are here" | Can post location pings | Read-only (sees where they are) |
| Keep / Cut / Maybe | Can set marks | Hidden / display-only |
| Signature 15 | Can tick "bagged" | Display-only |
| Kit & Admin | Visible | Hidden |
| Sights & roads | Separate tiles | Combined "Sights & Roads" tile with a Signature↔Passes toggle |
| Reset & clear panel | Visible (end of Info) | Hidden |
| Copy voice | First-person "we/us" | Third-person following-along "they" (never references a "brothers version") |

## Screens & features (walkthrough)

Design language: warm cream paper (`#f1e8d0` / `#e8dcbf`), dark ink (`#26201a`), rust-red accent (`#a8412a`), amber warnings (`#b0812c`), green progress (`#3f7a3f`-ish). Fonts: **Oswald** (display/labels), **Spectral** (serif body), **Space Mono** (mono micro-labels/tags). Subtle paper-grain overlay. Everything is a fixed-width phone column centered on a "desk" background.

1. **Landing gate** — countdown to trip start, title, map, brother/guest buttons (see Roles).
2. **Home** — countdown; a live **"We're here / Where they are"** location card (with post form for brothers); an amber offline banner when items are queued; an auto-sliding **Postbox** card (latest first, dot nav, swipe); an auto-sliding **Journal** card (latest 5, swipe); a tile grid: Campsites, Kit & Admin (brother), Postbox, Journal (brother order: Campsites | Kit & Admin, then Postbox | Journal); trip stats.
3. **Days** — list of ride days; each opens a **day detail** with the route caption, stops in order, campsite, and (brother) keep/cut/maybe controls per stop.
4. **Today** — the "today" view: pre-trip it shows a countdown footnote; on-trip it's driven by the date **and** the keep/cut/maybe decisions.
5. **Camp(sites)** — campsite list with booking flags (some marked "book this week").
6. **Sights & roads** — Signature 15 (headline spots, tick to bag) and Passes (biker roads). Guests get one combined screen with a toggle.
7. **Postbox** — board of F&F messages. Guests get a compose form (name = "Full Name", a **custom tap-to-open reason dropdown** — deliberately not a native `<select>`, which rendered blank on iOS — and free text). Brothers read and can remove. Posts show name, reason, relative time, and full message.
8. **Journal** — day-by-day aggregated record with timestamps, pulling from: location pings, keep/cut/maybe decisions, Signature bags, postbox messages, and the brothers' own notes. Brothers get a composer (author Paul/CJ, tag dropdown incl. "Other" free-text, optional day picker) and per-entry **edit/remove**. Top of screen: a **swipe carousel of the latest entries**; full chronological list below. Brothers also get **Save Trip Book (PDF)** and **Backup (JSON)** buttons.
9. **Info / The Guide** — a full, role-aware walkthrough of every feature, with example tag/chip imagery and a mock live-location banner. Guest copy is follow-along only. At the very bottom (brother only) sits the **Reset & clear** panel: Clear postbox / Clear pings / Clear journal / Clear marks, plus **Reset everything** — each behind a `window.confirm`, and each clears both local + cloud.
10. **Map** — hand-built SVG of Ireland with the WAW route as a coastline polyline, day markers, landmarks, cities, and the live pin. **Green progress line:** the route + points from the start (Malin Head) down to the current posted position render green ("done"); the rest renders in the default ink. Appears on the landing gate, home, and full-map view.

### The green progress map (how it works)
The route (`offPline` / projected `eOff`) is an ordered north→south coordinate list (Malin Head → Kinsale). The current position comes from the latest `locations` ping. The line is split at the current latitude: the northern (completed) portion is stroked green, the southern (remaining) portion default. Points north of the current latitude also render green. Preserve this "completion" semantic in the rebuild.

### Trip Book (PDF export)
A print stylesheet hides the app chrome (`.waw-noprint`) and lays out the journal as a printable document with a cover, then triggers the browser print dialog (save as PDF). It's a keepsake that works even after the hosted link is gone. In the rebuild, either replicate via `@media print` + `window.print()` or generate a PDF server-/client-side; the content is the full journal record.

## Known issues & improvement opportunities (good first tasks for Claude Code)
- **Everything lives in one ~2,300-line file.** Split into components/modules; this is the single biggest maintainability win.
- **Open RLS.** Fine for a private link, but consider a write gate or Supabase Auth if the link spreads.
- **Full re-pull on every realtime event.** Works at this tiny scale; could be incremental.
- **Secrets are in the client** (anon key) — expected for Supabase anon usage, but document it.
- **The single-file bundle self-unpacks**, which tripped up iOS "Add to Home Screen" earlier. A normal multi-file static build (Vite output) avoids this entirely — a reason the rebuild also fixes a real bug.
- **Accessibility / semantics** — the design is `<div>`-heavy inline styling; a rebuild is a chance to add proper roles/labels.

## Migrating Netlify → Cloudflare Pages

Good news: hosting is trivial because the app is static + a hosted backend. Nothing about Supabase changes.

**Option A — deploy the current build as-is (no rebuild):**
1. In the Cloudflare dashboard → **Workers & Pages → Create → Pages → Upload assets** (direct upload).
2. Upload the single `index.html` (drag it in). Publish. Done — you get a `*.pages.dev` URL.
3. (Optional) add a custom domain under the Pages project's **Custom domains**.

**Option B — deploy the rebuilt Vite app (recommended after the rebuild):**
1. Push the new repo to GitHub.
2. Cloudflare Pages → **Connect to Git** → pick the repo.
3. Build settings: **Build command** `npm run build`, **Output directory** `dist` (Vite default), framework preset "Vite".
4. Every push to `main` auto-deploys. Custom domain as above.

**Caching note (the bug we hit before):** browsers cache the app aggressively. After any redeploy, hard-refresh or use a private tab to confirm the new version. A Git-connected Pages project fingerprints assets on build, which largely eliminates this.

**Supabase:** no change. If you later add a custom domain, you may want to note it, but the anon client works from any origin with the current open policies.
